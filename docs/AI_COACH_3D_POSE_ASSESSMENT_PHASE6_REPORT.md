# AI 코치 3D 자세 측정 — Phase 6: 기준 각도에 맞춘 촬영 안내와 시점 판정

작성일: 2026-11-15 · 원본 프로젝트에서 작업 · 백업: `MARTIALDEX_backups/phase6-3dangle-20261115-150712`

## 요약

사용자가 3D 기준 영상의 각도를 고르면, 그 각도는 기준 영상과 함께 저장되어 촬영 화면까지 그대로 이어진다. 촬영 화면은 각도, 카메라 배치 그림과 설명, 기준 영상 미리보기, 촬영 전 확인 사항을 보여 준다. 사용자가 "이 각도에 맞춰 배치했다"고 확인해야 촬영이나 파일 업로드를 할 수 있다. 영상의 시점을 바꾸거나 맞추는 기능은 만들지 않았다. 앱은 안내하고, 찍힌 방향을 **확인**만 한다.

판정 쪽에서는 로컬 자세 추정과 Gemini가 각각 시점 일치 여부를 본다. 시점 때문에 보이지 않은 기준은 "틀림"이 아니라 "판단 불가"가 된다. 방향이 다르거나 확인할 수 없으면 신뢰도를 "높음"으로 표시하지 않고 재촬영을 안내한다. 점수 계산식은 바꾸지 않았다.

검증 중에 별도 결함을 하나 찾아 고쳤다. 3D 기준의 평가 기준 생성이 **운에 따라** 실패하는 문제였다(4절).

| 실제 Gemini 검증 | 방향 판정 | 판단 불가 처리 | 점수 | 신뢰도 |
|---|---|---|---|---|
| A. 대각선 3D 기준 + 정면 사용자 (Phase 5와 같은 조건) | **불일치** (로컬·Gemini 모두) | C2 궤적, C4 팔꿈치 신전 | 75 (Phase 5: 50) | **보통** 0.73 + 재촬영 안내 |
| B. 측면 3D 기준 + 측면 사용자 | **일치** | 없음 | 70 | **높음** 0.99 |

## 1. 사용자 촬영 흐름 변경 사항

1. 기술 선택 → 기준 영상 비교 → **3D 시연 녹화**
2. 각도 선택: 클립에 정의된 각도(정면·45° 대각선·측면·후면). 기본값은 대각선이고, 정면을 고르면 "앞으로 뻗는 동작은 정면에서 길이가 안 보입니다"라는 안내가 나온다. "고른 각도는 저장되고 촬영 때 같은 각도로 안내됩니다"라는 설명을 표시한다.
3. 실제 3D 렌더링 녹화 → 기존 기준 영상 등록 경로 → 기존 평가 기준 생성(Gemini)
4. **촬영 화면**(1-1)에서 기준 각도를 안내하고, 사용자가 각도를 확인한 뒤 카메라 또는 파일로 촬영
5. 기존 비교 엔진(정렬 → Gemini 판정 → 기존 점수 계산) → 결과에 **촬영 방향 확인** 표시(3절)
6. 각도를 바꾸려면 촬영 화면이나 결과 화면의 **"다른 각도로 기준 영상 다시 녹화"** 버튼을 누른다. 3D 녹화 화면이 바로 열리고, 새 각도의 기준 영상이 **별도로 추가**된다(기존 기준은 남음). 이어서 새 기준이 선택된다.

### 1-1. 촬영 안내 UI (`FormCompareModal.tsx` CaptureStep)
- **기준 각도**: "기준 각도: 45° 대각선 (3D 기준 영상을 녹화할 때 내가 고른 각도)"
- **배치 그림**: 위에서 본 그림으로 나·바라보는 방향·카메라 위치를 각도별로 보여 준다. 측면·대각선은 3D 프리셋과 같은 앞손 쪽이다.
- **카메라 배치 안내**: 각도별 위치 설명과 "제대로 놓였다면 화면에 이렇게 보입니다" 설명
- **기준 영상 미리보기**: 녹화한 3D 기준 영상을 반복 재생한다(YouTube 기준은 해당 구간 재생).
- **촬영 전 확인 사항**: 전신, 카메라 고정, 밝기, 같은 스탠스, 시작·종료 자세
- **각도 재확인 체크**: "카메라를 45° 대각선 각도에 맞춰 배치했습니다". 체크해야 "촬영 시작"과 파일 업로드가 활성화된다.
- **실시간 방향 추정**: 카메라가 켜진 동안 약 0.5초마다 표시한다(비슷함 / 판단 어려움 / 다른 방향 / 확인 불가). "추정"으로 표시하고 촬영을 막지는 않는다(2-2절의 정확도 한계 때문).
- 데스크톱·모바일(390px) 폭에서 화면을 캡처해 레이아웃을 확인했다.

## 2. 선택한 각도의 전달과 저장

- 3D 기준의 각도는 `source.angle`(사용자가 고른 값)과 `cameraView`에 저장된다(Phase 3 구조 그대로).
- 새 `referenceAngle()`이 기준 각도를 결정한다. **3D 기준은 사용자가 고른 각도가 확정값**이며, Gemini 프로필이 다른 방향을 말해도 덮어쓰지 않는다. 파일·YouTube 기준은 Gemini가 본 방향을 쓰고, 그것이 없으면 사용자가 입력한 방향을 쓴다.
- 기준 영상 목록 칩과 기준 카드에 각도를 표시한다("3D 시연 · 45° 대각선", "내가 고른 각도: 측면").
- 앱을 새로 읽어도 각도가 유지되는지 실제 UI로 확인했다(5절 [5]).
- **기술 변경**: 비교 모달은 기술이 바뀌면 키로 새로 만들어진다(`FormCompareModal` → `FormCompareModalInner key={technique.id}`). 모달이 열린 채 다른 기술 페이지로 이동하면 기존에는 이전 기술의 단계 상태(`capture`)가 남아 빈 모달이 되었다. 이제 새 기술의 처음 단계에서 시작한다.

### 2-2. 로컬 방향 추정의 실측 정확도
기존 추정기(어깨 너비 ÷ 몸통 길이)를 같은 클립으로 측정했다.

| 입력 | 실제 | 추정 |
|---|---|---|
| Blender 테스트 영상 6개 | 정면 5, 측면 1 | 5개 맞음 (정면 다른 외형 1개 → 대각선) |
| 3D 녹화 | 정면 / 대각선 / 측면 / 후면 | 정면 / **측면** / **대각선** / **정면** |

이 추정기는 카메라 위치가 아니라 카메라에 대한 **몸통 방향**을 잰다. 복싱처럼 몸을 비스듬히 세운 스탠스에서는 값이 한 칸 밀리고, 앞뒤는 구분하지 못한다. 그래서 다음처럼 처리한다.
- 사용자 추정값을 명목 각도가 아니라 **같은 추정기로 잰 기준 영상의 값**과 비교한다(같은 편향끼리).
- 정면 ↔ 측면처럼 분명히 다를 때만 "불일치 의심", 인접 각도는 "판단 어려움", 후면이 끼면 "확인 불가"로 본다.

## 3. 시점 불일치 경고 방식

`src/lib/formCompare/captureAngle.ts`의 `combineViewCheck()`가 두 신호를 합친다.

| 로컬 비교 | Gemini `viewCheck.relation` | 결과 |
|---|---|---|
| 불일치 | 무엇이든 | **불일치** (의심되면 경고) |
| 무엇이든 | different | **불일치** |
| 일치·판단 어려움 | same | 일치 |
| 일치 | (응답 없음) | 일치 |
| 그 밖의 모든 경우 | uncertain / 응답 없음 | **확인 불가** |

- **불일치**: 결과 화면에 경고(`role=alert`)를 띄운다. "기준 영상은 45° 대각선에서 촬영되었는데, 내 영상은 정면 등 다른 방향에서… 신뢰도를 '높음'으로 표시하지 않았습니다. 기준 각도에 맞춰 다시 촬영해 주세요." 근거로 Gemini의 설명을 함께 보여 주고, "45° 대각선 각도에 맞춰 다시 촬영" 버튼과(3D 기준이면) "다른 각도로 기준 영상 다시 녹화" 버튼을 둔다.
- **확인 불가**: "촬영 방향을 확인할 수 없습니다… 신뢰도를 '높음'으로 표시하지 않았습니다"라는 안내와 같은 버튼을 표시한다.
- **일치**: 확인 표시만 한다.
- **신뢰도**: 점수 계산식(`scoring.ts`)은 그대로다. 그 입력값 `viewMatches`를 이전의 "경고 문구가 없으면 true"에서 **"일치가 확인되었을 때만 true"**로 바꿨다. 기존 규칙이 방향이 다를 때 신뢰도를 0.74 이하로 묶으므로, 불일치와 확인 불가 모두 "높음"이 될 수 없다. 같은 판정이면 점수는 방향 결과와 무관하게 같다(단위 테스트로 확인).
- 비교 기록에는 `viewCheck`(기준 각도·출처, 로컬 결과, Gemini 결과, 최종 상태)를 저장한다. 기존 `viewWarning` 필드도 유지한다(불일치일 때 문구).
- 기존 `motion.ts`의 `viewWarning()`은 기존 QA 스크립트가 쓰고 있어 지우지 않았다. 앱 비교 경로에서는 더 이상 쓰지 않는다.

## 4. Gemini 판정 개선 결과

### 4-1. 프롬프트와 파싱 (`ai.ts`)
- 판정 전에 기준 프레임과 사용자 프레임의 카메라 방향을 비교해 `viewCheck {relation: same|different|uncertain, userView, note}`로 답하게 했다. 확실하지 않으면 uncertain이다.
- 방향 때문에 확인할 수 없는 기준은 mismatch로 단정하지 말고 `not_observable` + `viewLimited: true`로 두게 했다. 실제로 다르게 수행한 것이 보일 때만 mismatch다.
- 촬영 정보에 기준 각도와 그 출처("사용자가 3D 미리보기에서 직접 고른 각도 — 확정값")를 넣고, 로컬 추정이 틀릴 수 있다는 점도 함께 전달한다.
- **파싱 안전장치**: `viewLimited`인 mismatch·partial은 `not_observable`로, match는 확신도 low로 바꾼다. 이렇게 처리한 기준 목록은 결과 화면에 "촬영 방향 때문에 확인하지 못해 틀린 것으로 판정하지 않은 기준"으로 표시한다. 형식이 이상한 `viewCheck`는 응답이 없는 것으로 처리한다.

### 4-2. 실제 Gemini 결과 (`.devtools/qa-capture-angle-gemini.mjs`, 결과 `.last.json`)
사용자 영상은 Blender 합성 렌더다(`fixtures-form`, 정답 데이터상 둘 다 올바른 잽). **실제 사람이 촬영한 영상이 아니다.**

**A. 대각선 3D 기준 + 정면 사용자 영상(`jab_good`)** — Phase 5와 같은 조건
- 방향: 로컬 "불일치"(기준 추정 측면 ↔ 사용자 정면) + Gemini `different` ("기준 영상은 45° 대각선 구도인 반면, 사용자 영상은 정면을 향해 촬영되었습니다.") → **불일치 경고**
- 판정: C1 partial · **C2(궤적) not_observable** · C3 partial · **C4(팔꿈치 신전) not_observable** · C5 match · C6 match
  - C2 관찰: "정면 구도로 인해 앞손 펀치가 앞으로 뻗어나가는 직선 궤적과 깊이감을 정확히 구분할 수 없습니다."
- 점수 **75** (Phase 5에서는 같은 영상이 C2 "굽힌 채 멈췄다" mismatch/high로 50점), 관찰 가능 비중 0.63, 신뢰도 **보통 0.73**

**B. 측면 3D 기준 + 측면 사용자 영상(`jab_reference_side`)**
- 방향: 로컬 "판단 어려움"(추정 편향) + Gemini `same` → **일치**, 경고 없음
- 판정: C1 match · C2 match · C3 partial · C4 partial · C5 match → 점수 **70** (원점수 79, partial 2개로 상한), 신뢰도 **높음 0.99**
- partial 두 개 중 하나(C3)는 자세 추정 보조 신호가 match를 partial로 낮춘 것이다. 3D 마네킹과 Blender 캐릭터의 체형이 달라 생긴 차이로 보이며, 시점과는 무관하다(7절).

### 4-3. 검증 중 찾아 고친 결함 — 3D 기준의 평가 기준 생성이 운에 좌우됨
- 첫 실호출(A 기준 생성)에서 Gemini가 대각선 3D 녹화를 "Idle Guard Stance — 잽 아님"으로 판단했다. 스크립트는 그 자리에서 멈췄다(1건).
- **원인(무료 재현)**: 3D 마네킹에서는 MediaPipe가 동작 구간을 찾지 못한다(대각선 3회 중 3회 `no_movement`). 그러면 평가 기준용 프레임 10장이 파일 전체에서 균등하게 뽑힌다. 팔을 뻗은 약 0.25초가 그 안에 들어갈지는 lead-in 길이에 달려 있었다. 3회 중 1회는 뻗은 프레임이 **0장**이었다. Phase 5 2차 실행의 성공도 일부는 운이었다(Phase 5 보고서에 정정을 달았다).
- **수정** (`service.ts` `motion3dSegment()`): 3D 녹화는 "정지 구간 + 클립 1회 재생"이므로, 자세 추정이 구간을 못 찾으면 구간을 `[파일 길이 − 동작 길이, 파일 길이]`로, 정점을 클립의 `execute` 단계 끝으로 정한다. 실측과 일치했다(1636−1200=436ms → 뻗기 0.78–0.97s). 파일 길이를 모르면 추정하지 않는다. 공유 코드인 프레임 선택·자세 추정 로직은 바꾸지 않았다.
- **재검증(무료)**: 실제 등록 경로로 5회 녹화한 결과, 5회 모두 Gemini에 갈 프레임에 뻗은(또는 뻗는 중인) 프레임이 1–3장 들어갔다. 이후 실호출 A·B 모두 "Jab"으로 인식되었다.

## 7. 남은 문제

1. **실제 사람 촬영 영상 미검증.** 사용자 영상은 Blender 합성 렌더다. 실제 촬영에서 Gemini의 시점 판단과 로컬 추정이 얼마나 맞는지는 모른다.
2. **로컬 방향 추정의 한계.** 몸을 비스듬히 세운 스탠스에서 한 칸 밀리고, 앞뒤를 구분하지 못한다. 그래서 실시간 안내는 "추정"으로만 보여 주고 촬영을 막지 않는다. 후면 기준은 로컬로 확인할 수 없어 Gemini에만 의존한다.
3. **파일·YouTube 기준의 동작 변화.** 이제는 방향이 "확인된 경우"에만 신뢰도 "높음"이 나온다. 이전에는 방향을 알 수 없으면 일치로 간주했다. 이 경로의 유료 E2E(`qa-form-compare.mjs`)는 다시 실행하지 않았다.
4. **3D 기준과 사용자 체형 차이.** B 사례에서 자세 추정 보조 신호(H 힌트)가 마네킹과 사람 캐릭터의 체형 차이를 자세 차이로 보고 match를 partial로 낮췄다. 시점과는 별개 문제이며, 이번 범위에서는 바꾸지 않았다(채점 입력 규칙).
5. **Gemini의 `uncertain` 응답 미관측.** 확인 불가 경로는 단위 테스트로만 검증했다.
6. **판정 샘플 1회.** 같은 입력이라도 실행마다 판정이 달라질 수 있다.
7. **Android / Web 미검증**, 카메라 실촬영 경로 미검증(6절).
8. 기존 동작(이번 작업과 무관, 보고만 함): `#/arts/boxing/techniques/boxing__cross?open=pose`에서는 자세 분석이 열리지 않고 정규 id인 `kickboxing__cross`에서만 열린다. 같은 기술 페이지에서 `?open=pose`만 붙여 이동하면 모달이 다시 열리지 않는다.
